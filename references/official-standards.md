## 一、Agent Skills 开放规范（agentskills.io/specification）

Claude、ChatGPT / Codex、WorkBuddy、OpenClaw 等都声明基于这套开放格式，是跨平台可移植的最低公约数。

**目录**：技能是一个目录，至少包含 `SKILL.md`；可选 `scripts/`（可执行代码）、`references/`（按需读取的文档）、`assets/`（模板、图片、数据等静态资源）。

**frontmatter 字段**

| 字段 | 必填 | 约束 |
|------|------|------|
| `name` | 是 | 1–64 字符；只允许小写字母、数字、连字符；不能以连字符开头或结尾；不能有连续连字符；**必须与父目录名一致** |
| `description` | 是 | 1–1024 字符；写清做什么、什么时候用；包含帮助识别任务的关键词 |
| `license` | 否 | 许可证名称或包内许可证文件名 |
| `compatibility` | 否 | 1–500 字符；只在有特定环境要求时写（目标产品、系统包、网络访问等） |
| `metadata` | 否 | 字符串到字符串的键值表（作者、版本等扩展信息） |
| `allowed-tools` | 否 | 预先授权的工具，空格分隔；实验性，各平台支持程度不同 |

**渐进加载预算**：元数据（name + description）启动时常驻，约 100 tokens；触发后加载 `SKILL.md` 正文，建议少于 5000 tokens；其他文件按需加载。**`SKILL.md` 保持在 500 行以内**，细节放到单独文件。

> 本文件里的行数、token 数都是官方给的**参考值**，测试时只作参考，不作硬性判定。

**文件引用**：用相对技能根目录的路径；引用只深一层，避免引用链。

**校验工具**：官方参考库 `skills-ref`，命令 `skills-ref validate ./my-skill`，检查 frontmatter 和命名规范（需另行安装，本技能的 `skill_check.py` 已覆盖同等的命名与字段检查）。

## 二、Anthropic / Claude

来源：Claude 平台文档《Skill authoring best practices》、Anthropic 博客《Improving skill-creator: Test, measure, and refine Agent Skills》。

**frontmatter**：`name` 最长 64 字符，只允许小写字母、数字、连字符，不能含 XML 标签，不能含保留词 `anthropic`、`claude`；`description` 非空、最长 1024 字符、不含 XML 标签。

**命名**：推荐动名词形式（`processing-pdfs`），名词短语（`pdf-processing`）也可以；避免含糊的 `helper`、`utils`，避免过于宽泛的 `documents`、`data`；同一套技能的命名风格保持一致。

**description**：
- 始终第三人称（描述会注入系统提示，人称不一致会影响发现）。
- 写清做什么和什么时候用，包含具体触发词；模型要从上百个技能里靠它挑选。
- 反例：“Helps with documents”“Processes data”。

**写作原则**：
- **简洁**：默认模型已经很聪明，只写它不知道的；每段都问“这段值不值它占的 token”。
- **自由度匹配**：多种做法都对、依赖语境的，用文字原则（高自由度）；有偏好模式、允许变化的，用伪代码或带参数脚本（中）；脆弱、要求一致、必须按顺序的，用固定脚本（低自由度）。
- **渐进加载**：`SKILL.md` 正文 500 行以内；按领域拆参考文件；引用只深一层；超过 100 行的参考文件开头放目录。
- **工作流与反馈环**：复杂任务给分步清单；关键步骤加“校验 → 修正 → 再校验”的循环。
- **避免时效信息**：不写“2025 年 8 月之前用旧接口”，改成“当前做法”+“旧模式”段。
- **术语一致**：一个概念只用一个叫法。
- **示例具体**：给真实的输入输出示例，不写抽象描述。
- **少给选项**：给一个默认做法，再给例外，不罗列五个库让模型自己挑。

**带脚本的技能**：
- 脚本自己处理错误，不把问题甩给模型；参数值要有说明，不用“魔法数字”。
- 确定性操作优先给现成脚本（比让模型现写更可靠、省 token）；写清每个脚本是“运行”还是“阅读参考”。
- 批量、破坏性、高风险操作用“计划 → 校验计划 → 执行”，计划落成可校验的中间文件，校验脚本给出详细错误信息。
- 在 `SKILL.md` 列出所需的包；不要假设工具已安装，写出安装命令；注意不同运行环境的网络与安装限制。
- 引用 MCP 工具用完整名称 `服务名:工具名`。
- 路径只用正斜杠。

**测试与评估**：
- **评估先于文档**：先不用技能跑任务，记录失败点；为这些失败写至少三个评估场景；测出无技能基线；只写足以通过评估的最少指令；迭代对比。
- **用所有计划使用的模型测试**（官方举例：小模型看指导够不够，大模型看是否解释过度）。
- **观察模型如何浏览技能**：是否按意外顺序读文件、漏掉重要引用、反复读同一部分（应提到主文件）、某些文件从不读（可能多余或指引不清）。
- **skill-creator 的评测体系**（官方插件，可参考其方法）：每个用例在独立干净的上下文里运行；断言逐条判通过 / 失败并附证据；汇总通过率、耗时、token，对比带技能 vs 不带技能（或新旧两版）；盲评对比器在不知道哪个是新版的情况下评判；描述触发调优：生成应触发和不应触发的提问，测命中率并提出描述修改建议。官方博客提到：技能不再带来提升时，说明它可能已经不必要；模型更新后应重跑基准。

**官方清单（节选）**：描述具体且含关键词；写了做什么和何时用；正文少于 500 行；细节放单独文件；无时效信息；术语一致；示例具体；引用一层；工作流步骤清楚；脚本自己处理错误；无魔法数字；列出并核实依赖；无反斜杠路径；关键操作有校验步骤；质量关键任务有反馈环；至少三个评估；用真实场景测试。

## 三、OpenAI（ChatGPT / Codex）

来源：OpenAI《Build skills》文档。

- 基于 Agent Skills 开放标准；`SKILL.md` 必须有 `name` 和 `description`。
- **触发方式**：显式调用（ChatGPT 输入 `@` 选择，Codex 输入 `$技能名` 或 `/skills`）；隐式调用（任务与 description 匹配时自动选用）。
- **描述会被截断**：Codex 初始技能列表默认最多占上下文的 2%（未知时 8000 字符），技能多时先缩短描述，过多时可能省略部分技能。所以**把关键用途和触发词放在描述最前面**，写清范围和边界。
- **可选 `agents/openai.yaml`**：`interface`（`display_name`、`short_description`、图标、`brand_color`、`default_prompt`）、`policy.allow_implicit_invocation`（设为 false 时只能显式调用）、`dependencies.tools`（声明依赖的 MCP 等工具）。
- **同名技能不合并**：不同位置的同名技能会同时出现，需避免重名。
- **最佳实践**：每个技能专注一件事；除非需要确定性行为或外部工具，优先用指令而非脚本；用祈使句写步骤，明确输入输出；**用测试提问检验描述，确认触发行为正确**。
- 分发给他人时打包成插件（plugin）。

## 四、WorkBuddy 开放平台

来源：WorkBuddy 开放平台文档“技能”页（open.workbuddy.cn/docs/skill）。

**目录**：`SKILL.md`（必须）、`references/`、`scripts/`、`templates/`（均可选）。参考文件在 `SKILL.md` 中可用 `@references/xxx.md` 引用；脚本由 AI 通过 Bash 执行，需在 `SKILL.md` 写明调用命令和参数。

**上架到技能市场的 frontmatter 字段**

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | 是 | 技能标识 |
| `display_name` | 是 | 市场中文展示名 |
| `display_name_en` | 是 | 市场英文展示名 |
| `description` | 是 | 写清用途和触发词 |
| `description_zh` | 是 | 详情页中文简介 |
| `description_en` | 是 | 详情页英文简介 |
| `version` | 是 | 版本号 |
| `author` | 是 | 合作方名称 |
| `allowed-tools` | 否 | 工具白名单（逗号分隔） |
| `examples_zh` / `examples_en` | 否 | 详情页“试试这样用”案例 |

- 上传 zip 解析失败时，按“技能基础结构”和“子资源目录说明”排查。
- 本地自用技能不需要上架字段；**要上架时按上表补齐**。
- 社区教程中的经验（非官方规范，供参考）：description 写触发词；一个技能一件事；技能里不写死账号、路径等隐私；技能目录是 `.workbuddy/skills/`。

## 五、ClawHub / OpenClaw

来源：OpenClaw 官方博客《OpenClaw Partners with VirusTotal for Skill Security》；其他条目为社区发布经验，已标注。

**官方安全流程**：发布时技能文件被确定性打包并计算 SHA-256；用 VirusTotal 查询或上传扫描，Code Insight 从 `SKILL.md` 开始分析整个包实际做了什么（是否下载执行外部代码、访问敏感数据、进行网络操作、嵌入诱导代理做不安全行为的指令）；判定为良性自动通过，可疑标警告，恶意直接阻止下载；所有在架技能每天重扫。官方明确说明：**用自然语言诱导代理作恶、精心构造的提示注入不会被病毒特征发现**，扫描只是一层防护。

**社区发布经验（非官方，供参考）**：
- 每个脚本开头写“安全清单”注释：访问哪些环境变量、调用哪些外部地址、读写哪些本地文件。
- Shell 脚本 `set -euo pipefail`，校验参数和环境变量，用户输入进入命令前做转义。
- `SKILL.md` 写清外部地址表、数据去向、隐私说明。
- 发布包里不放 `.env`、`.git/` 等。
- 声明的能力与实际行为一致，不夸大（扫描会比对名称描述与实际行为）。
- 用语义化版本号。

## 六、各平台差异速查

| 项 | 开放规范 / Claude / Codex | WorkBuddy 本地 | WorkBuddy 开放平台上架 | ClawHub |
|----|------------------------|---------------|---------------------|---------|
| `name` 大写、空格、中文 | 不允许 | 实际可用 | 文档未限定，`[待确认]` 上架审核口径 | 按开放规范 |
| `name` 与目录名一致 | 要求 | 不强制 | 未说明 | 按开放规范 |
| 展示名 | Codex 用 `agents/openai.yaml` 的 `display_name` | — | `display_name` / `display_name_en` 必填 | — |
| 中英双语简介 | — | — | 必填 | — |
| 版本、作者 | 放 `metadata`（可选） | — | `version`、`author` 必填 | 语义化版本 |
| 安全扫描 | Claude 平台未公开扫描流程 | — | 未说明 | VirusTotal + Code Insight，每日重扫 |

**默认做法**：一律用开放规范名作为 `name` 和目录名（小写字母、数字、单连字符，如 `geo-buddy`），好记的名字放进展示名字段（frontmatter 的 `display_name`，Codex 用 `agents/openai.yaml` 的 `display_name`）。这样本地、跨平台、上架都不用再改名。

## 七、映射到本技能判项

| 官方要求 | 判项 |
|---------|------|
| name / description 字段约束、目录名一致 | T1-01 至 T1-04 |
| 描述写做什么 + 何时用、关键词前置、第三人称 | T1-05、T6 |
| 正文 500 行 / 5000 tokens、引用一层、长文件目录 | T2-01 至 T2-04 |
| 无时效信息、术语一致、示例具体 | T4-08、T4-06、T4-04 |
| 脚本自处理错误、无魔法数字、依赖声明、运行或阅读意图 | T5-03、T3-05、T5-06 |
| 计划—校验—执行、反馈环 | T5-11 |
| 至少三个评估、带 / 不带技能对比、多模型 | T7-02、T7-05 |
| 触发测试（应触发 / 不应触发） | T6-01、T6-02 |
| 观察模型如何浏览技能 | `eval-guide.md` 第四节 |
| 安全扫描关注点（下载执行、敏感数据、网络、诱导指令） | T8 |
