# 动态评测指南：触发、效果、对比

> 静态检查只能说明技能“写得对不对”，动态评测才能说明它“用起来灵不灵、有没有用”。本指南不依赖任何特定平台的插件；宿主支持子代理（独立上下文）时并行跑，不支持时按顺序在新会话里跑。

## 一、什么时候做动态评测

| 情况 | 做什么 |
|------|-------|
| 新建技能、准备上架 | 触发评测 + 至少三个效果用例 |
| 改了 description 或技能改名 | 触发评测 |
| 大改规则、结构 | 效果评测（新旧版本对比） |
| 模型或宿主平台升级 | 重跑效果评测，看技能是否仍有提升 |
| 用户只要快速体检 | 不做，报告里注明“未做动态评测” |

动态评测需要实际调用模型，耗时和 token 成本较高；开始前告诉用户大致规模（用例数 × 版本数）。

## 二、触发评测（T6）

### 2.1 写测试提问

- **应触发**：用户真实会说的话，口语化、带上下文细节；有的不提技能名，有的用缩写或错别字，有的只说结果（“帮我把这堆发票弄成表格”）。
- **不应触发**：选“近似误触”，即与本技能话题相近、但应由别的技能或不需要技能处理的请求（如本技能写公众号文章，近似误触是“帮我改一下这份合同里的措辞”）。明显无关的请求没有检验价值。
- **撞车提问**：同时可能命中本技能和另一个已安装技能的请求，用来检验分工是否清楚。
- 数量参考：应触发、不应触发各 8–10 条起步；技能多、描述相近时多写撞车提问。

### 2.2 怎么跑

1. 每条提问在**新会话**里发出（不带之前的上下文），只提供技能列表，不点名技能。
2. 记录模型选中了哪个技能（或没选）。
3. 同一提问跑 2–3 次，看结果是否稳定。
4. 宿主不暴露“选中了哪个技能”时，看它是否读取了该技能的 `SKILL.md`，或按技能的特征行为（固定的第一步、固定的输出格式）判断。

### 2.3 判定与改进

| 结果 | 含义 | 改法 |
|------|------|------|
| 应触发但没触发 | 描述缺少用户的真实说法，或关键用途藏在描述后半段 | 把真实触发词、核心用途前移；补“什么时候用” |
| 不应触发却触发 | 描述范围写得太宽 | 写清边界：“不用于……” |
| 撞车 | 两个技能都声称负责同一件事 | 调整分工，一方让出，或在描述里写清各自范围 |

**改描述时防止过拟合**：留出一部分提问不参与修改，只用来最后检验。

## 三、效果评测（T7）

### 3.1 写用例

- 从技能声称支持的场景里挑至少三个，覆盖主路径、一个边界情况、一个用户真实碰到过的难点。
- 每个用例写：提问、输入文件（如有）、期望行为（若干条断言）。
- **断言要客观可验证**：文件是否生成、格式是否正确、必含要素是否都在、数字是否与输入一致、有没有出现禁止项。名字要一看就知道在检查什么。
- **主观维度不硬写断言**：文风、审美、观点深度用人工评审，给评审者两份结果和评审要点。

### 3.2 对比怎么做

1. 同一用例跑两组：**带技能** vs **不带技能**（或 **新版** vs **旧版**），每组在独立的干净上下文中运行。
2. 每条断言判通过 / 失败，并写出证据（引用输出原文或文件路径）。
3. 汇总：通过率、耗时、token（宿主能提供时）。
4. 盲评：比较两份产出时，评审者不知道哪份来自新版或带技能。

### 3.3 怎么读结果

| 结果 | 含义 |
|------|------|
| 带技能明显好于不带 | 技能有价值，继续 |
| 两者差不多 | 技能可能只是复述常识，或模型已经学会；考虑精简或退役 |
| 带技能更差 | 技能里有误导规则、过度约束或冲突，按失败断言回查对应规则 |
| 新版不如旧版 | 本次修改引入问题，回退或修正后再测 |
| 通过率提升但 token 和耗时大增 | 评估成本是否值得，能否把内容下沉到按需加载 |

## 四、观察模型如何使用技能

跑用例时顺带记录（Anthropic 官方建议的观察点）：

- 是否按意外的顺序读文件——说明结构或指引不直观。
- 是否漏掉重要的参考文件——引用不够明显。
- 是否反复读同一个参考文件——这部分可能应该放进主文件。
- 是否从来没读过某个文件——文件可能多余，或者指引不清。
- 是否跳过脚本、自己现写代码——脚本的调用方式没写清楚。
- 是否给自己的自检全部打勾——自检设计成了自证，需要改成证据式。

## 五、评测文件格式

建议在被测技能目录下建 `evals/`（征得用户同意后再写入），格式参考 `assets/evals-template.json`：

```json
{
  "skill": "技能名",
  "trigger_cases": [
    {"query": "用户原话", "should_trigger": true, "note": "主路径"},
    {"query": "近似但不该触发的请求", "should_trigger": false, "note": "近似误触"}
  ],
  "eval_cases": [
    {
      "id": "E1",
      "query": "任务描述",
      "files": ["evals/files/input.xlsx"],
      "assertions": [
        "生成了 output.md",
        "输出包含输入中的全部 12 个字段",
        "没有出现输入中不存在的数字"
      ],
      "human_review": ["结论是否先行"]
    }
  ]
}
```

结果记录：每次评测把“用例 / 版本 / 每条断言结果与证据 / 通过率 / 耗时 / token”写进报告；需要回归时保留这份结果。

## 六、成本与取舍

- 动态评测按“用例数 × 版本数 × 重复次数”计费，先用 3 个用例跑通，再决定是否扩展。
- 输出可客观验证的技能（数据处理、格式转换、固定流程）适合断言评测；输出偏主观的技能（写作、设计）以人工评审为主，断言只查硬性要素（格式、必含项、禁止项）。
- 本技能的结论里必须写明做了哪些动态评测、哪些没做，不把静态检查的结论说成“实际效果已验证”。
